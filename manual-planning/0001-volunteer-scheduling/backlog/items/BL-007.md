## Summary

All five volunteer-dashboard Playwright specs authenticate as a leader (`LEADER_STORAGE_STATE`). They cover the correct UI flows but do not validate that a true volunteer session — one without leader permissions — can access and interact with the dashboard, and that the backend scopes data correctly for it.

## Full Context

A volunteer user has a different session context than a leader. Using `LEADER_STORAGE_STATE` in all E2E specs means:

- The specs confirm the UI renders correctly for an authenticated user.
- They do **not** confirm the backend correctly scopes assignments, availability and notifications when the caller lacks leader permissions.
- RBAC enforcement at the volunteer level is not exercised by the E2E layer at all.

Server-side `createCaller` integration tests are not a substitute: they exercise the service layer, not the authenticated HTTP path the volunteer actually travels.

## Suggested Approach

1. Replace `LEADER_STORAGE_STATE` with `VOLUNTEER_STORAGE_STATE` in the five specs above.
2. Run them. Any spec that now fails is triaged, **not** fixed in place: if the failure is a stale selector or a leader-only fixture assumption, fix it here; if it is the backend serving or accepting something a volunteer should not see, **file a new tier-1 backlog item** and leave the spec failing or skipped with a link to it.
3. Report the outcome on the issue either way — a clean pass is itself the deliverable, because it converts an unknown into a verified property.
