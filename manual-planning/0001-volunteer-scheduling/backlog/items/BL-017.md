## Summary

There is no "my roles" endpoint. Every role-based check in the frontend today — nav visibility (`use-caller-roles.ts`) and Spec 018 Phase 8's `/scheduling/planning-cycles` route guard — works by piggybacking on an admin-scoped endpoint and checking whether it 403s.

The one endpoint reused for this, `GET /admin/ministries` (`admin-leader-controller.ts`), only lets `ctx.isAdmin || ctx.isLeader` through, and `ctx.isLeader` is computed from `listLedMinistries` filtered on `systemRole = 'leader'` only. **A `sub_leader` membership 403s exactly like a plain volunteer**, so the frontend cannot tell the two apart.

## Full Context

### Concrete impact

`use-caller-roles.ts:23-38` derives `canSeeScheduling` purely from whether `adminApi.listMinistries()` 403s — with a doc comment that literally says *"There is no 'my roles' endpoint (research.md R1)"*. Despite the intent recorded in `data-model.md`'s `CallerNavVisibility` ("Leader, Sub-leader, or Church Admin capacity"), it silently evaluates to `false` for a sub-leader-only caller.

A sub-leader today therefore sees no "Scheduling" nav item at all.

### ⚠️ Correction to this item's original evidence

The original text claimed *"grepping all of `apps/server/src` for `sub_leader` yields zero guard/route/manager references anywhere outside the type union itself."* **That is false.** Reconciliation ([#10](https://github.com/tiagoluizpoli/church/issues/10)) found **9** references, including a real authorization branch at `db-event-manager.ts:74-81` that rejects plain volunteers and scopes a sub-leader to their led teams.

The **gap itself survives** — what is missing is a *lightweight, caller-facing* role signal the frontend can read, not sub-leader awareness in the domain layer. That distinction matters for the fix: the backend already knows how to recognise a sub-leader; it just never exposes that fact cheaply.

### Route-guard scope, corrected

The original suggested approach named `/scheduling/tailoring` **and** `/scheduling/builder-events`. **`/scheduling/builder-events` no longer exists** — retired by spec 023 ([New builder entry point](https://github.com/tiagoluizpoli/church/issues/8)). Only `/scheduling/tailoring` remains ungated.

### Why it was deferred originally

Fixing it needs new backend surface, which spec 018's Phase 8 explicitly could not introduce under its zero-new-backend-surface constraint. Phase 8 deliberately left the new scheduling routes **without** a role guard rather than reuse the buggy `listMinistries` check and make the exclusion worse.

## Suggested Approach

1. Add a lightweight endpoint (or extend an existing cheap one) whose `preValidation` allows `ctx.isAdmin || ctx.isLeader || ctx.isSubLeader`, computing `isSubLeader` the same way `isLeader` is computed today — a `listLedMinistries`-style query filtered on `systemRole = 'sub_leader'`.
2. Fix `use-caller-roles.ts` to read it, so sub-leaders see the Scheduling nav item.
3. Add the previously-skipped role guard to `/scheduling/tailoring`, now that a real signal exists to gate on — **after** BL-021 has moved the route files.

## Prerequisites / Dependencies

- **[BL-021](./BL-021.md)** must land first (route files relocate under `_authenticated.tsx`).
- Coordinate with [BL-011](./BL-011.md): whichever policy layer BL-011 builds should absorb this guard rather than leaving a second mechanism behind.

## Success Criteria

1. A caller-facing signal distinguishes `sub_leader` from plain volunteer without relying on a 403.
2. A sub-leader-only caller sees the Scheduling nav item.
3. `/scheduling/tailoring` is role-gated on that signal, and a plain volunteer typing the URL is refused.
