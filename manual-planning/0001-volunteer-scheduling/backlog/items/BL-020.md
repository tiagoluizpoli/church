# BL-020 — Re-applying a template after deleting cycle events generates nothing

**Status**: Backlog
**Feature area**: Scheduling / Planning (Admin Cycle View)

## Summary

In the admin cycle view, deleting an event removes it from the calendar UI, but re-applying the same template for those dates generates `0 events and 0 slots`. The template-generation dedupe logic still counts the deleted events as existing, so the user is left with an empty cycle that cannot be repopulated from the template.

## Full Context

Reproduced manually: apply the "Sunday services" template to a draft cycle, delete every generated event from the admin cycle view, then apply the same template again. Toast reports `Generated 0 events and 0 slots` and the calendar stays empty.

Root cause is a soft-delete/dedupe mismatch:

- The delete action is not a hard delete. `DbPlanningEventManager.cancelEvent`
  ([db-planning-event-manager.ts:641-666](apps/server/src/application/db-planning-event-manager.ts#L641-L666))
  only calls `updateEvent({ status: 'cancelled' })`. The row stays in `event`, and its
  `timeSlot` rows stay too.
- `generateFromTemplates`
  ([db-planning-event-manager.ts:148-199](apps/server/src/application/db-planning-event-manager.ts#L148-L199))
  builds its idempotency inputs from `eventRepository.listCycleEvents(...)`, which returns
  **all** events for the cycle regardless of status
  ([drizzle-planning-event.repository.ts:112-163](apps/server/src/infrastructure/repositories/drizzle-planning-event.repository.ts#L112-L163)).
- So the cancelled events land in `existingEvents` and their slots land in
  `existingFingerprints`, and the generator emits no `create_event` / slot plans for
  those dates.
- The web calendar hides cancelled events, hence "gone from the view" while the DB row
  still blocks regeneration.

## Suggested Approach

Decide the intended semantics first, then implement one of:

1. **Treat cancelled as absent for generation (smallest change)** — filter out
   `status === 'cancelled'` events when building `existingEvents` / `existingFingerprints`
   in `generateFromTemplates`. Then re-applying the template creates fresh events for
   those dates. Needs a decision on what happens to the orphaned cancelled row on the
   same date (leave it, or reuse/reactivate it).
2. **Reactivate on regeneration** — when the generator matches a cancelled event with the
   same `sourceTemplateId` + date, emit a plan that flips it back to `draft` and re-creates
   any missing template-block slots, instead of skipping it.
3. **Make delete a real delete for draft cycles** — hard-delete the event and its slots
   when the cycle is `draft` and the event was never staffed; keep the soft cancel only for
   locked cycles / already-scheduled events.

Whichever is chosen, the generator's dedupe must stay consistent with what the admin
cycle view shows: if the UI says an event does not exist, generation must agree.

## Prerequisites / Dependencies

- `apps/server/src/application/db-planning-event-manager.ts` (`generateFromTemplates`, `cancelEvent`)
- `apps/server/src/infrastructure/repositories/drizzle-planning-event.repository.ts` (`listCycleEvents`)
- The cycle-event generator's `existingEvents` / `existingFingerprints` contract
- Admin cycle calendar view in `apps/web/src/features/scheduling/components/planning-admin/`
- Related: [BL-016](./BL-016.md) (day/event-level editing on locked cycles) touches the same delete/reopen semantics.

## Success Criteria

1. Applying a template, deleting all generated events, then re-applying the same template
   regenerates the events and slots for those dates (non-zero counts in the toast).
2. Re-applying a template with events still present remains idempotent — no duplicate
   events or slots.
3. The admin cycle view and the generator agree on which events exist: nothing hidden in
   the UI silently blocks generation.
4. Regression tests cover: delete-then-regenerate, regenerate-without-delete (idempotent),
   and partial delete (some events removed, some kept).
