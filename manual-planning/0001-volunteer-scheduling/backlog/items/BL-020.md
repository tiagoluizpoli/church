**Feature area**: Scheduling / Planning (Admin Cycle View) — bug

## Summary

In the admin cycle view, deleting an event does **not** delete it — it soft-sets `status: 'cancelled'`. Re-applying the same template for those dates then generates `0 events and 0 slots`, because the generator's dedupe still counts the cancelled rows as existing. The admin is left with a cycle they cannot repopulate from its own template.

Reproduced manually: apply the "Sunday services" template to a draft cycle, delete every generated event, apply the same template again → toast reports `Generated 0 events and 0 slots`.

## Full Context

### The real root cause: `cancelled` means two things

One `Event.status` value carries both *"the admin removed this while drafting"* and *"this is terminally off the plan"*. That conflation — **not** a missing status filter in the generator — is what produces the bug.

Confirmed mechanisms:

- `DbPlanningEventManager.cancelEvent` (`db-planning-event-manager.ts:659-663`) only calls `updateEvent({ status: 'cancelled' })`. The `event` row stays, and its `timeSlot` rows stay with it.
- `listCycleEvents` (`drizzle-planning-event.repository.ts:112-161`) filters on `planningCycleId` + church isolation and has **no status predicate**.
- `generateFromTemplates` (`db-planning-event-manager.ts:163-198`) maps every returned event into `existingEvents` and every `sourceTemplateBlockId`-bearing slot into `existingFingerprints`, so no `create_event` plan is emitted for those dates.

### ⚠️ Correction — the original root-cause claim was false

The original text asserted: *"The web calendar hides cancelled events, hence 'gone from the view' while the DB row still blocks regeneration."* **Nothing is hidden.**

- `calendar-row.tsx:310-312` renders a status `Badge` for every row.
- `eventStatusBadgeVariant` (`planning-admin.utils.ts:221-233`) has an explicit `cancelled → 'destructive'` case.
- There is **no** `.filter(...)` dropping events anywhere on the `planning-admin.utils.ts` / `cycle-review-card.tsx` path.

What actually happens: the admin presses a destructive `Trash2 · Delete` button whose dialog reads *"Delete this day? — This removes "{title}" and its slots from the cycle"* (`planning-event-card.tsx:141-152`), the row **stays visible** wearing a red `cancelled` badge, and regeneration then reports zero. This is cleanly a **naming bug** — the UI promises removal and delivers a status change.

## Decided Approach — split delete from cancel

**The three options originally listed here are superseded.** The decision ([#12](https://github.com/tiagoluizpoli/church/issues/12)):

| Branch | Condition | Behaviour |
| :-- | :-- | :-- |
| **Delete** | `event.status === 'draft'` | **Hard delete** the event row |
| **Cancel** | anything else (`scheduled`, …) | **Soft cancel**, byte-for-byte today's behaviour — silent, no notification, no acknowledgment |

### Why publication is the right line

`publish` is **per-Event, not per-cycle** — `assignment-manager-service.ts:220-314` requires `event.status === 'draft'`, then calls `event.markScheduled()` and flips assignments `draft → pending`. So `Event.status` *already is* the "have volunteers been told?" flag. A `draft` event was never published, so deleting it destroys nothing anyone saw; a `scheduled` event was announced, so removing it is itself an announcement.

This reuses the exact predicate `ensureWritableEvent` (`db-planning-event-manager.ts:613-615`) already guards on, and needs no "was it staffed" query. **Cycle state was rejected as the line**: a *draft* cycle can hold staffed events (the builder assigns before locking), so `cycle.state === 'draft'` would hard-delete assignment rows out from under work already done.

### The consequence that shrinks this item: **the generator needs no change at all**

Under the split, `generateFromTemplates` becomes correct as written:

- Draft events are hard-deleted, so they never appear in `listCycleEvents`, so fresh `create_event` plans are emitted for those dates. **Bug fixed.**
- Cancelled events now genuinely mean *"this service is not happening"*, so the generator continuing to skip those dates is **desired** — re-applying a template must not silently resurrect a deliberately cancelled service.

`existingEvents` / `existingFingerprints` and `CycleEventGenerator` are untouched. The entire fix lives in `cancelEvent` plus a new repository method.

### Domain rules this preserves

`PlanningCycle.assertCanReopenEvent` (`planning-cycle.ts:93-100`) already declares `cancelled` and `past` terminal, refusing `cancelled → draft`. The split **reinforces** that rule — which is why "reactivate on regeneration" was rejected: it would have required either deleting that guard or explaining why the generator may perform a transition `reopenEvent` is forbidden to perform.

## Implementation Notes

1. **`deleteEvent` does not exist.** Neither `domain/contracts/infrastructure/planning-event.repository.ts` (contract) nor `drizzle-planning-event.repository.ts` (impl) has any delete method. **Adding one is the bulk of the work.**
2. **Cascade is already safe.** `event → timeSlot → shift → assignment` are all `onDelete: 'cascade'` (`packages/db/src/schema/scheduling.ts:69`, `:110`, `packages/db/src/schema/assignments.ts:30`), as is `assignmentAudit → assignment`. A hard delete cleans up slots, shifts, draft assignments and their audits with no FK block and no orphans. Audit loss is acceptable precisely because a `draft` event was never published — `event_published` and friends cannot exist yet.
3. **UI copy stays as-is.** The `Delete` button and its dialog become *true* on the draft branch, the overwhelmingly common case. Making the scheduled branch read honestly (*"Cancel this service? Volunteers have already been notified…"*) is deliberately left to [BL-016](./BL-016.md), which owns the announcement layer.

## Success Criteria

1. Applying a template, deleting all generated draft events, then re-applying the same template regenerates the events and slots for those dates (non-zero counts in the toast).
2. Re-applying a template with events still present remains idempotent — no duplicate events or slots.
3. *(Retired — nothing is hidden in the UI. Under the split, a visible cancelled row correctly blocking that date is the intended meaning, not a defect.)*
4. Regression tests cover: delete-then-regenerate, regenerate-without-delete (idempotent), partial delete, **and** cancel-a-scheduled-event-then-regenerate — which must produce zero events for that date, asserting the non-resurrection property.
