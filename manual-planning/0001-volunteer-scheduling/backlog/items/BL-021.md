**Status**: Ranked — wave 1, rank 1
**Feature area**: Authentication & Routing (`apps/web`, `packages/auth`)

## Summary

The application operates on an administrative invitation model. Public self-registration must be suppressed, the one remaining unguarded route closed, `/login` taken out of the app chrome, and the five duplicated per-route auth guards folded into a single pathless layout.

## Full Context

### Sign-up suppression — valid as written, and the sharp end of this item

- `apps/web/src/routes/login.tsx:16` initialises `useState(false)` and renders `SignUpForm` **first** — public self-registration is not merely reachable, it is the default face of `/login`.
- `sign-in-form.tsx:14` types `onSwitchToSignUp: () => void` as **required** and renders the toggle at `:136`, so hiding it does mean making the prop optional, exactly as proposed below.
- `packages/auth/src/index.ts:18` enables `emailAndPassword`, so suppressing the UI alone leaves the credential path open.
- `packages/auth/src/hooks/soft-registration.ts:35` soft-registers every new user as an **`active` volunteer in `system-church`** — the reason this is a live authorization concern and not a cosmetic one.

### Route protection — already largely done, but scattered

The original premise ("all application features must be protected") is mostly satisfied today. **Five** routes already run a `getSession()` → `redirect({ to: '/login' })` guard in `beforeLoad`:

- `routes/scheduling.tsx:6-12`
- `routes/scheduling/planning-cycles.tsx:9`
- `routes/dashboard.tsx:22-33`
- `routes/notifications.tsx:10`
- `routes/volunteer/availability.tsx:11`

### What actually remains — three narrower gaps

1. **`/` is unguarded.** `routes/index.tsx` has no `beforeLoad` at all — the landing page with its Dashboard / Availability / Scheduling cards renders for an unauthenticated visitor. This is the only genuine hole in route coverage, and it is small.
2. **`/login` renders inside the app chrome.** `__root.tsx` mounts `<AppShell>` around `<Outlet />` unconditionally, so the sidebar and header wrap the sign-in page.
3. **The guard is duplicated five times.** The pathless `_authenticated.tsx` layout is a **de-duplication**, not new protection.

> ⚠️ The original route list named `routes/availability.tsx` as a page to protect. It is now a pure redirect to `/dashboard?section=availability`.

### Relationship to BL-011

Same shape as [BL-011](./BL-011.md), opposite end of the stack: the same auth check copy-pasted across N call sites. They share no files and neither blocks the other. But note the coupling recorded in [Controller cluster](https://github.com/tiagoluizpoli/church/issues/11): the server-side `/admin/schedule-builder` carve-out exists **only** because `/scheduling` guards on authentication alone. Adding a role guard to `/scheduling` makes that carve-out removable — do not remove it as part of this item, just record it.

## Suggested Approach

Single pass, because all of it edits the same route files.

1. **Sign-up suppression**
   - Make `onSwitchToSignUp` optional in `sign-in-form.tsx` and hide the toggle when omitted.
   - `login.tsx` renders `<SignInForm />` directly and redirects authenticated users back to `/`.
   - Close the credential path itself, not only its UI — otherwise `emailAndPassword` sign-up remains callable.
2. **Route protection & layout separation**
   - Simplify `__root.tsx` to render `<Outlet />` inside `ThemeProvider`, without `<AppShell>`.
   - Introduce `src/routes/_authenticated.tsx` with a `beforeLoad` session check.
   - Move `/`, `/dashboard`, `/notifications`, `/scheduling`, `/volunteer/*` under it, wrapped in `AppShell`, and **delete the five now-redundant per-route guards**.

## Prerequisites / Dependencies

- Better Auth session client, `apps/web/src/lib/auth-client.ts`.
- TanStack Router file-based route tree in `apps/web`.

## Success Criteria

> **Superseded** by [`specs/024-invite-only-registration/spec.md`](../../../../specs/024-invite-only-registration/spec.md) §12 (SC-001 … SC-034), which restates these as checkable statements and adds the tenancy, provisioning, invitation, delivery and transfer criteria this item did not anticipate. Kept here as the original framing.

1. Public sign-up is unreachable from `/login` **and** the self-registration path no longer mints a `system-church` volunteer for a stranger.
2. Unauthenticated visits to `/` or any internal route redirect to `/login`.
3. `/login` renders standalone, without sidebar/header chrome.
4. Exactly one auth guard exists in the route tree; the five per-route duplicates are gone and authenticated users still reach every private route with `AppShell` intact.
5. Route guard behaviour is covered by Playwright E2E verification.
