# BL-022 — Cycles & Rostering Behavioral & Feature Parity

**Status**: Backlog  
**Feature area**: Frontend UX/IA & Feature Parity (`apps/web`)

## Summary

Align the Planning Cycles workspace (`/scheduling/planning-cycles/*`) to match the interaction and design standards of the Rostering/Tailoring workspace (`/scheduling/tailoring/*`). Replaces full-column/row click targets in Cycles with explicit action buttons and dropdown menus, standardizing headers and workflow interaction patterns.

## Full Context

Interaction patterns between Planning Cycles and Rostering have diverged:
- In Planning Cycles, whole columns/rows are clickable, creating ambiguity about row selection vs. item navigation.
- In Rostering/Tailoring, explicit action buttons and dropdown menus are used to manage items cleanly.
- Header statistics, empty states, and action toolbars between the two feature areas have minor discrepancies that need to be unified so the product feels like one cohesive system.

## Suggested Approach

1. Refactor Planning Cycles tables to replace full-column/row click handlers with explicit Action Buttons / Dropdown Menus matching Rostering conventions.
2. Align header stats, breadcrumbs, action toolbars, and empty states in Planning Cycles to match Rostering/Tailoring conventions.
3. Standardize desktop vs. mobile view behaviors across both workspaces.

## Prerequisites / Dependencies

- Planning Cycles routes (`/scheduling/planning-cycles/*`)
- Tailoring / Rostering workspace routes (`/scheduling/tailoring/*`)

## Success Criteria

1. Planning Cycles table interactions match Rostering (explicit action buttons/menus replace whole-row click ambiguity).
2. Header statistics, toolbars, and empty states in Cycles match Rostering standards.
3. Existing `data-testid` selectors remain intact for E2E tests.
