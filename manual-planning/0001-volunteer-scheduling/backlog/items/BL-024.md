## Summary

Promote `workspace-page.tsx` past its current two exports into a `WorkspaceHeader` API carrying stat pills and an action toolbar, and bring the Planning Cycles workspace onto it — so page headers across domains compose from one centralized API instead of being re-implemented per page.

## Full Context

### Why it is a separate item from `DataTable`

`DataTable` and `WorkspaceHeader` share no code and no consumer list: **six** table call sites versus **ten** `WorkspacePage` / `WorkspaceIntroPanel` consumers. Bundling them would have made one item that touches two unrelated component families for two unrelated reasons.

### Current state (verified 2026-07-26)

- `apps/web/src/components/workspace-page.tsx` exports **exactly two** symbols — `WorkspacePage` and `WorkspaceIntroPanel` — across **10** consumers.
- There is **no** `WorkspaceHeader`, no stat-pill primitive and no action-toolbar primitive. Each page re-implements them.
- The Cycles workspace is still on raw `Card` / `CardHeader` / `CardTitle` (`cycle-list-card.tsx:49-54`), which is precisely the discrepancy [BL-022](./BL-022.md) originally complained about. Rehousing that clause here means **`cycle-list-card.tsx` is not edited twice for the same reason**.

### The builder-critique track is a consumer, not a competitor

`.plan/handoffs/023-builder-critique-backlog.md` ticket **B-4 shipped 2026-07-24**, and the entire `B-1`…`B-9` track is done. B-4 produced `apps/web/src/features/scheduling/components/builder/cycle-builder-header.tsx`, which **already imports `WorkspaceIntroPanel`**. So it is a reference implementation, not a fifth bespoke header to migrate later: this item **generalises the primitive B-4 already builds on**, and B-4's file is the compatibility test the extracted API must keep serving.

## Suggested Approach

1. Extract a `WorkspaceHeader` API from the header layouts currently hand-rolled across the ten `WorkspacePage` consumers — title/description block, **stat pills**, and an **action toolbar** — keeping `WorkspaceIntroPanel`'s existing contract intact so `cycle-builder-header.tsx` continues to compile unchanged.
2. Move the Planning Cycles workspace off raw `Card` / `CardHeader` / `CardTitle` onto the new primitive.
3. Align toolbars and empty states across Cycles and Rostering in the same pass — the parity clause inherited from BL-022.

## Prerequisites / Dependencies

- `apps/web/src/components/workspace-page.tsx`
- `apps/web/src/features/scheduling/components/planning-admin/cycle-list-card.tsx`
- `apps/web/src/features/scheduling/components/builder/cycle-builder-header.tsx` — existing consumer, must keep working.
- No dependency on [BL-022](./BL-022.md) or [BL-023](./BL-023.md).

## Success Criteria

1. `WorkspaceHeader` centralizes header layout, statistics badges and the action toolbar, and `WorkspaceIntroPanel`'s existing consumers are unaffected.
2. The Cycles workspace renders through the primitive rather than raw `Card` primitives.
3. Header statistics, toolbars and empty states in Cycles match the Rostering/Tailoring conventions *(inherited from BL-022 success criterion 2)*.
4. A single change in `WorkspaceHeader` propagates across all consuming pages.
