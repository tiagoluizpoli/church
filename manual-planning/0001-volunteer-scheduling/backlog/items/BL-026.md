# BL-026 — Volunteer dashboard has no visible state for zero Church access

> ## 🅿️ Parked 2026-07-30 — not queued, no rank
>
> The gap is real but nobody has hit it yet. Surfaced during code review of #53 (route-tree consolidation), not from a user report — no evidence this has actually confused anyone in practice.
>
> **Promotion trigger** — A User reports (or QA/support observes) a blank, unexplained dashboard after losing Church access, **or** [#54](https://github.com/tiagoluizpoli/church/issues/54) (Active Church selector and switcher) lands and defines the system-wide no-access/selection-required presentation — at which point the dashboard's error state should adopt that pattern rather than invent its own, and the two should land together.

**Status**: Parked
**Feature area**: Volunteer Dashboard

## Summary

`useVolunteerDashboard` (`apps/web/src/features/volunteers/hooks/use-volunteer-dashboard.ts`) surfaces no page-level error/empty state distinct from "nothing to show." A User with zero Church Memberships — or whose sole Church Membership was revoked — landing on `/dashboard` gets a query that 401s server-side (`requireVolunteer: true` on the volunteer-controller routes, enforced by `createActiveChurchPreValidation`), but the hook only destructures `.data` with `??` fallbacks to empty arrays. The result is a dashboard that renders as if the User simply has nothing scheduled, not one that explains they have no Church access at all.

## Full Context

Found while implementing #53 (Consolidate the authenticated route tree). The new `_active-church` guard (`apps/web/src/routes/_authenticated/_active-church.tsx`) intentionally lets a session with no `activeOrganizationId` yet pass through to mount the shell — the auto-select-on-single-membership side effect only happens inside the child route's own Church-scoped fetch (see the comment at `_active-church.tsx:10-15`). That's the correct trade-off for the guard itself, but it means the dashboard's own query is the last line that could tell the User *why* nothing is showing, and today it doesn't.

This is not new to #53 — the old per-route `dashboard.tsx` guard only ever checked session existence too, so the underlying query behavior is unchanged. It was simply never surfaced before because nobody had reason to look at this exact path.

## Suggested Approach

Surface `dashboardQuery.isError` / `dashboardQuery.error` in `VolunteerDashboard` and distinguish a 401/no-membership response from a generic fetch failure, showing an explanatory state instead of a silently-empty one. Whatever shape this takes should match whatever no-access presentation [#54](https://github.com/tiagoluizpoli/church/issues/54) settles on, rather than being designed in isolation — hence the promotion trigger tying the two together.

## Prerequisites / Dependencies

- Ideally sequenced with or after [#54](https://github.com/tiagoluizpoli/church/issues/54), so the dashboard's error state reuses one system-wide pattern instead of a one-off.

## Success Criteria

1. A User with zero Church Memberships (or a revoked sole membership) landing on `/dashboard` sees an explanatory state, not a blank "nothing scheduled" dashboard.
2. The distinction between "no Church access" and "a transient fetch failure" is visible to the User (the two need different next actions).
3. The presentation matches whatever no-access pattern #54 establishes elsewhere in the app.
