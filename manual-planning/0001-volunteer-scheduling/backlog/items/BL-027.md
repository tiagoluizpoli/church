# BL-027 — No `AbortSignal` wiring for in-flight requests

> ## 🅿️ Parked 2026-07-30 — not queued, no rank
>
> Surfaced during `/code-review` of [#79](https://github.com/tiagoluizpoli/church/issues/79) (cross-tab Active Church synchronization). The gap is real but nobody has hit it as an incident yet — it is a latent race window, not an observed failure.
>
> **Promotion trigger** — a confirmed incident (or a reproducible test) where a request dispatched just before an Active Church switch lands under the wrong Church's session context after the switch completes, **or** a second, unrelated need for true request cancellation shows up (e.g. an expensive report/export call that should stop the moment its triggering screen unmounts) and justifies building the plumbing once rather than twice.

**Status**: Parked
**Feature area**: Frontend Architecture / Data Layer

## Summary

No API call site in `apps/web/src` wires an `AbortSignal` into its request. `queryClient.cancelQueries({ predicate })` (used by `switchActiveChurch` since [BL-021](./BL-021.md)'s #78, and now also by the cross-tab sync guard from #79) only stops React Query from committing an in-flight response to cache — it does not abort the underlying HTTP request. A request dispatched an instant before a Church switch (same-tab or cross-tab) can still complete and, if it's a mutation, write under the new Active Church's session context.

## Full Context

Found while reviewing `apps/web/src/shared/utils/active-church-switch.ts` and `apps/web/src/shared/hooks/use-active-church-tab-sync.ts`: both call `cancelQueries`/`clearActiveChurchScopedCache` on switch, matching NOTES.md's "cancels in-flight Church-scoped requests" language, but that language is satisfied only at the React Query layer, not the network layer. Grepping `apps/web/src/infrastructure/api` and `apps/web/src/utils/api-instances.ts` for `signal` found zero hits — this is a codebase-wide gap, not something introduced by #78 or #79, and fixing it for one call site without a plan for the rest would be inconsistent.

## Suggested Approach

- Thread `AbortSignal` from React Query's `queryFn`/`mutationFn` context into the generated Orval client (`apps/web/src/infrastructure/api`) and the shared axios instance (`apps/web/src/utils/api-instances.ts`).
- Once available, `switchActiveChurch` and the cross-tab continue handler can abort in-flight Church-scoped requests instead of only removing them from cache.

## Prerequisites / Dependencies

None blocking — this is additive plumbing, not gated on other backlog items.

## Success Criteria

1. Every generated API client call accepts and forwards an `AbortSignal`.
2. `switchActiveChurch`'s query cancellation actually aborts the underlying HTTP request, not just the cache write.
3. A regression test demonstrates a request in flight at switch time is aborted rather than allowed to complete and write under the new Active Church.
