# BL-028 — Centralize test trees and make repository rules agent-enforceable

> ## 🅿️ Parked 2026-08-11 — not queued, no rank
>
> The test layout is inconsistent, but no delivery work is currently blocked by it and placing a repository-wide migration into the ranked queue would assert an ordering decision that has not been made. The current mismatch is nevertheless actively creating avoidable discovery and import-boundary risk as new tests are added.
>
> **Promotion trigger** — The next planned implementation that adds, moves, or substantially rewrites a unit, component, integration, contract, or test-support file promotes this item; alternatively, one additional test file is added beside production code after this item was recorded. Either event makes the migration's rework cost immediate.

**Status**: Parked
**Feature area**: Repository Architecture / Test Infrastructure / Agent Governance

## Summary

Establish one enforced repository convention: executable tests and test-only support code live in a package-local isolated test tree that mirrors the production source path, never next to production implementation. Migrate the existing mixed layout without changing the behaviour or classification of the test suite.

At the same time, make the repository's operating rules discoverable and binding for every supported coding agent. The test-placement rule must be part of the same concise, project-owned rule source as the existing architecture, parameter-contract, validation, and workflow rules; it must not become an isolated convention that only one agent entry point sees.

## Full Context

The repository currently follows two incompatible patterns:

- `apps/server/tests/` already holds most server tests and test support, but `apps/server/vitest.config.ts` also discovers `src/**/*.test.ts`; source-adjacent tests remain in API controllers, application, domain services, infrastructure services, the main process, and contract-test runners.
- `apps/web/tests/` holds Playwright specs, while Vitest discovers unit, component, and integration tests directly from `apps/web/src/**`. Web test setup is also under `src/__tests__/setup`, and many source-adjacent tests import it through source-relative paths.
- `packages/auth` and `packages/db` already use `tests/**`; `packages/core` has a test configuration with implicit discovery. The end state must be coherent across all executable packages, not a web-only relocation.

This is more than a file move. The Vitest projects, coverage scope, path aliases, direct/relative test-helper imports, Playwright configuration, and changed-file validation all encode parts of the present layout. A mechanical move can silently omit tests, run a test in the wrong project, break coverage, or allow test-only helpers to leak into production imports.

Repository rules are currently distributed: the shared `AGENTS.md` establishes general protocol, `agents.local.md` carries project-specific architecture and validation rules, `CLAUDE.md` tells Claude to read the local context and governance documents, and the constitution carries non-negotiable principles. `AGENTS.md` is a shared symlink and must not be edited for project-specific work. The eventual solution therefore needs a single project-owned canonical rule source, explicit precedence, and entry-point wiring/verification for every agent supported by this repository without duplicating or weakening the constitution.

## Suggested Approach

1. Inventory every executable `*.test.*` and `*.spec.*` file, plus test-only fixtures, doubles, setup modules, contract runners, and global setup/teardown. Classify each as unit, component, integration, contract, or E2E before moving it.
2. Define and document one per-package test-tree shape. Each non-E2E test must sit under the package's isolated test root and preserve its production-relative path; test kind may be represented by a stable directory and/or suffix, but discovery must be declarative rather than a growing list of individual files. Keep E2E in its own explicit test subtree and preserve Playwright's global setup/teardown behaviour.
3. Move all source-adjacent test files and test-only support out of `src/`. Keep production code importing only production modules; provide a dedicated test-only import path/alias for fixtures, setup utilities, test doubles, and SUT builders, and update imports accordingly. Do not turn test helpers into production modules merely to make imports convenient.
4. Update each affected Vitest/Playwright configuration, package script, Turbo task, coverage include/exclude, and affected-file validation rule so every moved test runs exactly once in its intended project and its source file remains attributed correctly for coverage.
5. Add an automated repository guard, with tests for the guard itself, that rejects new executable test files below production source trees and rejects any prohibited production-to-test import. Deliberately documented tooling/configuration exceptions are allowed only where they are part of test execution rather than production runtime.
6. Consolidate existing repository rules into one concise, project-owned canonical context with a clear precedence order: constitution for non-negotiables; the canonical local rule set for project conventions; feature plans/specs for scoped work. Link to it from every supported agent bootstrap/context mechanism rather than copying the rules into multiple documents. Preserve the shared-`AGENTS.md` protection: project work updates the local companion context, never the shared symlink.
7. Verify a fresh agent context for each supported agent family can locate the canonical rule set before modifying code, and make that check maintainable as agent tooling evolves.

## Prerequisites / Dependencies

- No functional feature dependency. The migration must be planned as its own repository-architecture change because it touches test discovery and enforcement across multiple workspaces.
- Retain the current test taxonomy and all existing coverage thresholds unless a separately approved decision changes them.
- The implementation plan must identify the supported agent entry points present at that time; it must not assume that a document is automatically loaded merely because it exists in the repository.

## Success Criteria

1. Every executable unit, component, integration, contract, and E2E test, together with its test-only support modules, resides in an isolated package-local test tree; no executable test remains under a production `src/` tree or beside its implementation file.
2. The isolated tree mirrors the corresponding source path consistently across affected packages, and each test retains its intended runner/project classification (including server unit vs. integration and web unit vs. component vs. integration vs. Playwright E2E).
3. Test-only fixtures, doubles, setup utilities, and SUT builders are imported through an explicit test-only boundary; production runtime code has no dependency on that boundary.
4. Vitest, Playwright, Turbo, coverage, and changed-scope validation discover every migrated test exactly once. Existing test commands and coverage thresholds remain green without silently narrowing coverage.
5. A checked-in automated guard prevents future source-adjacent executable tests and prohibited production-to-test imports, and the guard has regression coverage for allowed and rejected paths.
6. One project-owned, agent-visible rule source states the test-placement convention alongside the repository's existing rules, defines its authority relative to the constitution and feature plans, and is referenced by every supported agent bootstrap/context path without editing the shared `AGENTS.md` symlink.
7. The repository documentation identifies the canonical location for future rules so an agent or developer does not need to infer conventions from the current file layout.
