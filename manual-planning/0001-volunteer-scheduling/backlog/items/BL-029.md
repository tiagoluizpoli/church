# BL-029 — Planning managers read wall-clock `new Date()`, so time-relative tests rot

> ## 🅿️ Parked 2026-09-10 — not queued, no rank
>
> The gap is real but nobody is blocked: every occurrence so far is fixed by
> bumping hardcoded dates a year forward, which just restarts the countdown.
> Surfaced during BL-020 ([#21](https://github.com/tiagoluizpoli/church/issues/21))
> implementation, recorded so the underlying cause is not forgotten the next
> time a green suite turns red on its own.
>
> **Promotion trigger** — a **second** time-rot failure lands on `master` or
> blocks a PR (i.e. a dated test asserting time-relative behaviour fails only
> because the wall clock moved past its fixtures), **or** any planned change
> needs to inject a clock into `DbPlanningEventManager` /
> `DbPlanningCycleManager` for a feature reason and this work rides along.

**Status**: Parked — not queued
**Feature area**: Test Infrastructure / Scheduling (Planning managers)

## Summary

`DbPlanningEventManager.ensurePlanningCycleWritable` (and the sibling
lazy-archive path in `DbPlanningCycleManager`) call `new Date()` directly to
decide whether a planning cycle has expired (`today >= cycleEnd` →
auto-archive → `IllegalStateTransitionError`). Nothing can freeze that clock,
so any test that hardcodes absolute calendar dates and exercises this path
passes until real time crosses the fixture date, then fails for a reason
unrelated to the code under test.

Give the planning managers an injected `Clock` (the abstraction already
exists — `apps/server/src/test-support/clock.ts`, `FixedClock`, used by
`scheduling-phase5.volunteer-availability.test.ts` and
`availability-overlap.test.ts`) and have the date-sensitive planning tests
drive it with a `FixedClock` instead of live wall time.

## Full Context

Concrete instance (BL-020, 2026-09-10): the test
`rejects a manual event whose start date falls outside the planning cycle` in
`apps/server/tests/application/planning-phase3.managers.test.ts` built a cycle
running `2026-08-01 → 2026-09-01`. On 2026-09-10 the wall clock was already
past `2026-09-01`, so `ensurePlanningCycleWritable` archived the cycle and the
call threw `IllegalStateTransitionError` before it could reach the
`EventOutsidePlanningCycleError` the test asserts. It had nothing to do with
BL-020; it only showed up because the affected-test gate runs the whole
touched file. The fix applied was mechanical — the fixture dates were bumped
to 2027 — which resets the same trap for ~1 year.

Why it recurs: `planning-phase3.managers.test.ts` alone hardcodes ~30 absolute
dates across cycle/event fixtures, and several other files
(`scheduling-phase*.test.ts`) follow the same pattern. Any of them that
touches cycle expiry, event `past` transitions, or "today" comparisons is a
latent time bomb with a different fuse length.

- `DbPlanningEventManager.ensurePlanningCycleWritable` —
  `apps/server/src/application/db-planning-event-manager.ts` (`instant: new Date()`)
- `DbPlanningCycleManager` lazy-archive path —
  `apps/server/src/application/db-planning-cycle-manager.ts`
- `Clock` / `FixedClock` —
  `apps/server/src/test-support/clock.ts` (already the project idiom;
  `getCurrentChurchDate({ clock, timeZone })` is the shaped accessor)

## Suggested Approach

1. Add a `Clock` constructor dependency to `DbPlanningEventManager` and
   `DbPlanningCycleManager` (tsyringe token, defaulting to a system clock that
   returns `new Date()`), and replace the direct `new Date()` reads with
   `getCurrentChurchDate({ clock: this.clock, timeZone })`.
2. In `createManagers()` in `planning-phase3.managers.test.ts`, pass a
   `FixedClock` pinned to a stable instant the suite controls; rewrite the
   date-sensitive tests to position fixtures relative to that instant
   (before / inside / after the cycle window) rather than by literal year.
3. Optionally add a small `tests/scheduling-reshape/setup.ts` helper that
   derives cycle/event dates from the fixed instant so future tests do not
   reintroduce literals.

## Prerequisites / Dependencies

- None. Self-contained in `apps/server`. No schema change.
- Light overlap with [BL-028](./BL-028.md) (test-tree governance) — this is the
  behavioural half (injectable time), not the file-layout half.

## Success Criteria

1. `DbPlanningEventManager` / `DbPlanningCycleManager` take an injectable
   `Clock`; production wiring uses a system clock, tests use `FixedClock`.
2. The date-sensitive planning-manager tests position fixtures relative to a
   suite-controlled instant and contain no bare hardcoded future years for the
   "is the cycle still writable" assertions.
3. Advancing the real calendar by an arbitrary amount does not change the
   pass/fail result of the planning-manager suite (verifiable by running it
   with a `FixedClock` set years ahead).
