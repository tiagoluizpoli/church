## Summary

Four operations exist twice, under two different route trees, two different OpenAPI tags, and two different application-layer managers, but with the same request/response shape:

| Operation | ChurchAdmin path (`church-admin-controller.ts`, tag `planning`) | Leader path (tag `events`/`time-slots`) |
| :--- | :--- | :--- |
| Create a TimeSlot | `POST /admin/planning-cycles/:cycleId/events/:eventId/slots` → `createPlanningEventSlot` → `planningEventManager.createSlot` | `POST /events/:eventId/slots` → `createSlot` (`time-slot-controller.ts`) → `eventManager.createSlot` |
| Update a TimeSlot | `PATCH .../events/:eventId/slots/:slotId` → `updatePlanningEventSlot` → `planningEventManager.updateSlot` | `PATCH /events/:eventId/slots/:slotId` → `updateSlot` → `eventManager.updateSlot` |
| Delete a TimeSlot | `DELETE .../events/:eventId/slots/:slotId` → `deletePlanningEventSlot` → `planningEventManager.deleteSlot` | `DELETE /events/:eventId/slots/:slotId` → `deleteSlot` → `eventManager.deleteSlot` |
| Cancel an Event | `POST .../events/:eventId/cancel` → `cancelPlanningEvent` → `planningEventManager.cancelEvent` | `POST /events/:eventId/cancel` → `cancelEvent` → `eventManager.cancelEvent` |

`createPlanningEventSlot`/`createSlot` both take `createSlotBodySchema` and return `timeSlotResponseSchema` — verified byte-identical body/response wiring, just called through a different controller and a different manager instance.

## Full Context

Found while writing BL-012's route descriptions: `createPlanningEventSlot`'s and `createSlot`'s summaries ended up nearly identical ("Create a TimeSlot on an Event") because the two routes really do the same thing. The standards review of that commit flagged the wording overlap as a mild doc-maintenance smell — a wording fix would have to land in two places — which prompted checking how deep the duplication actually goes. It goes past the docs: it's two parallel implementations, `IPlanningEventManager` and `IEventManager`, each with their own `createSlot`/`updateSlot`/`deleteSlot`/`cancelEvent` methods doing the equivalent domain operation.

The two paths differ only in **caller** (ChurchAdmin operating within a specific PlanningCycle vs. a Ministry leader operating on an Event directly) and **auth guard** (`church-admin-controller.ts`'s controller-level `canManageChurch` hook vs. `event-controller.ts`/`time-slot-controller.ts`'s per-route `denyEventScope`). Whether that caller distinction is worth two full parallel implementations, or whether the admin path should simply reuse `IEventManager` under its own auth guard, is the open question — not something to resolve inside a documentation sweep.

Related to [BL-011](./BL-011.md) (already implemented on this branch: `refactor(server): split controller routes by domain, not caller role (BL-011)`, commit `73ce0f9`), which split the old `admin-leader-controller.ts` into today's domain controllers but did not touch `church-admin-controller.ts`'s own pre-existing overlap with the routes it split out. This item is the residue BL-011 left behind, not a regression it introduced.

## Suggested Approach

Not scoped yet — the two candidate directions are (a) have `church-admin-controller.ts`'s four routes delegate to `IEventManager` directly, dropping the `IPlanningEventManager` duplicates, with the ChurchAdmin-specific auth guard staying at the controller level, or (b) keep both surfaces but have one implementation call through to the other so there is only one behavior to fix. Needs a decision on whether the ChurchAdmin-nested path (scoped to a specific `cycleId`) is meant to diverge from the leader path in ways that would make a shared implementation awkward — e.g., does creating a slot from the admin path need to validate the event belongs to the given cycle in a way the leader path does not.

## Prerequisites / Dependencies

None blocking. Worth checking whether `IPlanningEventManager.createSlot`/`updateSlot`/`deleteSlot`/`cancelEvent` and `IEventManager`'s equivalents have already diverged in validation or side effects before assuming a straight merge is safe.

## Success Criteria

1. Each of the four operations (create/update/delete TimeSlot, cancel Event) has exactly one application-layer implementation, called from both route trees (or the redundant route tree is removed, if that turns out to be the right call).
2. No behavior change to either route's response shape, status codes, or auth semantics for existing callers.
3. Existing tests for both `church-admin-controller.test.ts` and `event-controller.test.ts`/`time-slot-controller.test.ts` pass unmodified (or are updated only to reflect an intentional, reviewed behavior decision).
