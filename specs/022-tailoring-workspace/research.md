# Phase 0 Research: Tailoring Workspace Reorganization

## R1: Route structure for ministry → cycle → tailoring

**Decision**: Replace flat `apps/web/src/routes/scheduling/tailoring.tsx` with a nested layout tree mirroring the existing `planning-cycles` convention:

```
routes/scheduling/tailoring.tsx                                  # layout route (outlet only)
routes/scheduling/tailoring/index.tsx                             # Story 1: ministry list
routes/scheduling/tailoring/$ministryId.tsx                       # layout route (outlet only)
routes/scheduling/tailoring/$ministryId/index.tsx                 # Story 2: cycle list for that ministry
routes/scheduling/tailoring/$ministryId/$cycleId.tsx               # Story 3+4: tailoring workspace
```

**Rationale**: Matches `routes/scheduling/planning-cycles.tsx` + `planning-cycles/index.tsx` + `planning-cycles/$cycleId.tsx` exactly — same TanStack Router file-based nesting pattern already used one level away in the same feature area. Keeps URL state (ministryId, cycleId) as route params, which the existing `participation-tailoring.tsx` currently holds as component state instead — this is the mechanical fix for "revisit this screen at any time" (FR-017): a bookmarkable/shareable URL replaces in-memory selection.

**Alternatives considered**: Keep the flat route and add ministry/cycle as query params — rejected because it breaks from the established nested-route precedent in the same codebase area and makes deep-linking to a specific ministry+cycle awkward (query params don't compose with router loaders/breadcrumbs as cleanly as path params here).

## R2: Extraction strategy for `participation-tailoring.tsx`

**Decision**: Split the current ~1000-line monolith by responsibility, preserving all existing mutation call sites and payload shapes verbatim:

- `ministry-tailoring-list.tsx` — Story 1 (table/card list), built on the responsive pattern in `cycle-list-card.tsx`.
- `ministry-cycle-list.tsx` — Story 2 (cycle picker scoped to one ministry).
- `tailoring-calendar.tsx` — new month-grid calendar with day markers and day-click filtering (see R3).
- `tailoring-filters.tsx` — name + time-of-day filter controls, operating client-side over already-fetched data.
- `tailoring-slot-list.tsx` — the compact, flat, day-grouped per-slot list. **Post-critique decision**: this component fully **replaces** `ParticipationEventCard`'s rendering role — it does not sit alongside it. The original plan named both a new compact list and an "extracted, unchanged" event card without saying which owned rendering; left unresolved, the current triple-nested-card structure (`Card` → `surface-subtle` slot row → `surface-panel` shift panel) would have survived underneath a cosmetically-compact wrapper. `ParticipationEventCard` is **not** extracted as a standalone file; its per-slot/per-shift *markup* is superseded by `tailoring-slot-list.tsx`'s flat, ring-bordered row structure (matching `cycle-list-card.tsx`'s pattern — no card-in-card). Only its non-visual logic (mutation call shapes, prop wiring to `setParticipationInclusions`/`splitParticipationShifts`) carries forward into the new component.
- `manual-split-editor.tsx` — extracted verbatim from its current inline definition at the bottom of `participation-tailoring.tsx` into its own file; internal logic (`validateManualSpans`, equal/manual strategy payloads) is **not** rewritten. Its DOM structure (native `<select>`, unsized number inputs) **is** rewritten to use shadcn `Select` and `touch`-sized inputs — only the validation/payload logic is verbatim, not the markup, per the pre-build critique's P2 finding that "reuse logic unchanged" was ambiguous about DOM structure too.
- `participation-tailoring.utils.ts` — kept as-is; extended only with pure helpers needed for calendar day-marker computation and client-side filtering (no changes to existing exports' signatures).

**Rationale**: The constitution's Domain-First / separation-of-concerns rule and the spec's own reuse constraint both push toward extraction-not-rewrite. Every existing mutation (`setParticipationInclusions`, `splitParticipationShifts`, `upsertShiftRequirement`, `fireAvailability`, `resendAvailabilityReminder`) keeps its current orval-generated signature; only the components calling them move.

**Alternatives considered**: Rewrite the tailoring form logic against a new state shape — rejected per explicit spec assumption ("existing slot-inclusion, shift-split, and headcount data and persistence behavior are reused as-is").

## R3: Month calendar with day markers — three-layer visual state (post-critique decision)

**Decision**: Build on `react-day-picker`'s **range** mode (already available via the shadcn range-picker block referenced by the user — https://ui.shadcn.com/docs/components/base/date-picker#range-picker), rendered inline/always-open (not inside a `Popover` trigger, unlike `DatePickerField`), with three visually distinct, simultaneous states so the calendar never overloads one signifier with two meanings:

1. **Cycle bounds (fixed, non-interactive)**: the cycle's `startDate`→`endDate` renders as the range-picker's soft "in-range" band (the muted background tint range-picker already uses for days between the two selected endpoints), applied permanently via a `disabled`-outside-range + always-on `modifiers.range_middle`/`range_start`/`range_end`-equivalent styling. The leader cannot drag or edit this — it is not a selection, it is a fixed structural marker of the cycle. Month navigation is bounded so the leader can never scroll outside `[startDate, endDate]`.
2. **Event-day marker (dot)**: unchanged from the original plan — a small dot on any day present in the `Set<ISODateString>` from `buildEventDayMarkers`, layered on top of the band.
3. **Active day-filter (interactive)**: clicking a marked day sets `selectedDate`; rendered as a **ring/outline** treatment, not a solid fill. Clicking again (or a "Clear filter" affordance) resets it. This is deliberately *not* the solid-primary-fill "committed date" style used by `DatePickerField`/event-creation elsewhere in the app — that signifier means "I have chosen and saved this date" system-wide, and reusing it here for a transient, reversible filter would mistrain leaders about what that fill means the next time they see a real date-picker (flagged as a P0 in the pre-build critique, `.impeccable/critique/2026-07-11T21-00-35Z__kspace-tailoring-workspace-redesign-plan-pre-build.md`).

**Rationale**: `react-day-picker`'s range mode already ships the two-tier "endpoint vs. in-range" visual vocabulary needed to separate "structural cycle boundary" from "user's active filter" without inventing new CSS from scratch — extending the existing shadcn range-picker block satisfies both the constitution's "Strict shadcn/ui Adherence" rule and the critique's consistency concern in one move. Building a bespoke calendar would have violated the "DO NOT CREATE IT FROM SCRATCH" rule; reusing a *different existing shadcn variant* (range vs. single) than originally planned is still "using what's there."

**Alternatives considered**: Single-day `modifiers.selected` styling (original plan) — rejected post-critique because it collides with the solid-fill "committed date" meaning used elsewhere. A completely custom `<table>`-based month grid — rejected as unnecessary reinvention. A third-party full calendar library — rejected, out of proportion and not an existing dependency.

## R4: "Fire once per save" — reconciling with the existing per-participation API

**Decision**: No backend change is required. Server-side dedup already exists: `AvailabilityCheck` rows are unique per `(planningCycleId, ministryVolunteerId)` (`packages/db/src/schema/availability-checks.ts`, unique index `availability_check_cycle_membership_idx`), and `DbAvailabilityCheckManager.fireAvailability` (`apps/server/src/application/db-availability-check-manager.ts:46-124`) only creates checks and sends notifications for memberships that don't already have one for that cycle. Calling `fireAvailability(participationId)` once per touched `MinistryParticipation` in the cycle therefore produces **exactly one** notification per volunteer for that cycle, regardless of how many events/participations are involved — the current per-participation API already satisfies the spec's notification-count requirement at the data layer.

The gap is purely in the frontend: today the leader must open each event's participation individually and click "fire" per event. The new tailoring workspace instead exposes **one** explicit "Save & request availability" action per ministry+cycle visit, which internally calls `fireAvailability` for every `MinistryParticipation` touched in that session (sequentially or in parallel), while presenting a single pending/success state to the leader. Each individual call still performs its own `tailoring → availability_fired` state transition (a real per-participation state machine step, per `ministry-participation.ts`), but the volunteer-facing effect is the single batched notification the spec requires.

**Rationale**: Avoids inventing a new bulk backend endpoint for a guarantee the system already provides; keeps the change scoped to presentation, matching Spec 018's precedent of shipping IA/workflow changes without new backend contracts where the domain already supports the desired behavior.

**Alternatives considered**: Add a new `POST /cycles/:cycleId/ministries/:ministryId/fire-availability` bulk endpoint — deferred; would be a nice-to-have simplification of the frontend orchestration but is not required to meet SC-004, and the spec's governance explicitly scopes backend enforcement work as something that "can lag frontend." Revisit only if per-call overhead becomes a measured problem.

## R5: Ministry-list zero-state vs. `defaultDirection: 'all_in'` ministries

**Decision**: Display actual counts always — do not special-case a forced "0" for any ministry. Most ministries default to `defaultDirection: 'all_out'` (schema default, `packages/db/src/schema/core.ts`), which is why the spec's "starts at zero" framing holds for the common case. But a ministry configured `all_in`, or one with an applicable `MinistryServingProfile` standing rule, will have inclusions **pre-seeded** the moment a cycle's events are generated (per `CONTEXT.md`'s `MinistryParticipation` and `MinistryServingProfile` glossary entries) — before the leader has manually touched anything. In that case the ministry list correctly shows non-zero counts on first visit, which is accurate, not a bug.

**Rationale**: The spec's own event/slot counts (FR-002, FR-003) are defined as reflecting real participation state, not "has the leader manually acted." Silently forcing zero for untouched-but-pre-seeded ministries would misrepresent already-committed standing coverage.

**Note for spec**: This refines (does not contradict) spec Assumption 1 — recorded here rather than as a spec edit since it's a clarification of "actual counts," not a new requirement.

## R6: Claimed-elsewhere vs. self-reported-unavailable (FR-019)

**Decision**: This distinction does not exist anywhere in the current domain model, ADRs, or `manual-planning` refinement docs — confirmed by search across `CONTEXT.md`, ADR 0001/0002, and `refinement-02-scheduling-reshape.md`. It is genuinely new domain surface, not a rediscovery of existing behavior.

Minimal schema note (no implementation this feature, per spec's explicit deferral): the existing `Availability` entity (an unavailability mark hanging off an `AvailabilityCheck`, atomic to a `Shift` — `packages/db/src/schema/availability-checks.ts`) has no field capturing *why* a shift is unavailable to a given ministry beyond the volunteer's own mark. Representing "claimed by another ministry's published Assignment" requires either (a) a computed/derived state at query time (join against `Assignment` rows for the same volunteer at overlapping `Shift` times across other `MinistryParticipation`s) rather than a stored column, or (b) a new enum/state on a per-(ministry, volunteer, shift) view. Recommend (a) — derived, not stored — as the default direction for the future assignment-screen work, since "claimed" is inherently a function of the current state of *other* ministries' assignments and would go stale immediately if persisted as a static flag. This is documented in `data-model.md` as a **notes-only** entry; no migration is part of this feature's task list.

**Alternatives considered**: Add a stored `unavailability_reason` enum column now — rejected for this feature; write-now-for-later columns with no consuming code violate the "minimum code" / no-speculative-abstraction guidance, and the derived-vs-stored decision genuinely depends on the future assignment screen's query patterns, which aren't designed yet.

## R7: Single-cycle auto-advance (post-critique P1)

**Decision**: When a ministry has exactly one cycle currently open for tailoring, `routes/scheduling/tailoring/$ministryId/index.tsx` redirects directly to that cycle's `$cycleId` workspace instead of rendering a one-item picker. The cycle-list URL remains directly reachable (e.g. via back navigation) and renders normally whenever 2+ cycles are open.

**Rationale**: The pre-build critique (P1) flagged that FR-005/006 as originally written force every leader through a full-screen "choice" between zero real options, contradicting PRODUCT.md's framing of leaders working in short, repeat, between-service sessions. Auto-advancing removes a zero-value screen for the common case (most leaders manage few concurrently-open cycles per ministry) without removing the screen for the case where it's actually useful.

**Alternatives considered**: Always show the cycle list regardless of count — rejected, it's the exact friction the critique flagged; skip the cycle-list route entirely — rejected, it's still needed for the multi-cycle case and for deep-linking.

## R8: Unsaved-changes protection (post-critique P1)

**Decision**: The tailoring workspace route (`$ministryId/$cycleId.tsx`) tracks a dirty flag whenever any inclusion/split/headcount edit is made and not yet saved, and registers a navigation-blocking confirmation (TanStack Router's `useBlocker` or equivalent) so leaving the route — including closing the tab — prompts a "you have unsaved changes" confirmation before discarding. This is presentation-only; no local-storage draft persistence is added in this feature (that would be a larger, separate offline-drafts feature).

**Rationale**: The pre-build critique (P1) noted PRODUCT.md's own description of leaders working "in short sessions between other tasks" — an interruption (a call, a service starting) with zero unsaved-changes warning silently loses real work. A navigation-blocking confirm is the minimum viable fix; full draft persistence is out of scope for this feature per the "minimum code" guidance — it's a real but separable improvement to revisit if the confirm-on-exit proves insufficient in practice.

**Alternatives considered**: Full local-draft autosave — deferred, meaningfully larger scope (storage schema, conflict resolution with server state, staleness handling) than this feature's budget; no protection at all — rejected per the critique.

## R9: Fixing the pre-existing `.surface-panel` shadow (post-critique P2)

**Decision**: Remove the resting `box-shadow` from `.surface-panel` in `apps/web/src/index.css` (currently contradicts the design system's own documented "cards/panels never get a resting shadow, only a ring/border" rule) as part of this feature's implementation, since every new tailoring-workspace card is built on this primitive and would otherwise silently inherit the bug.

**Rationale**: This is a shared, app-wide primitive — fixing it here benefits every existing screen that uses `surface-panel`, not just the tailoring workspace, and removes the inheritance risk at its source rather than working around it locally. The change is a single CSS property removal, low risk, and directly enforces the design system's own written rule.

**Scope note**: Because `.surface-panel` is used outside this feature's screens too (any existing `Card` with `className="surface-panel"`), this fix has a blast radius slightly wider than specs/022's own surfaces. It is still a one-line, purely visual (shadow-removal) change with no behavioral risk — flagged here explicitly so it isn't a silent side effect buried in an unrelated task.

**Alternatives considered**: Leave it and let new tailoring cards inherit the same (buggy) look for pixel-consistency with the rest of the app today — rejected per explicit user decision; the design system's own rule is unambiguous and the fix is trivial.

## R10: Ministry-list data-fetch contract and "cycle set" definition (post-analyze C1/A1)

**Decision**: No new backend endpoint. Confirmed via codebase check: `listMinistries()` returns no counts (`apps/server/src/api/dtos/ministry.dto.ts:4-19`), and `getCycleParticipation` is single-cycle/single-ministry with no aggregate field (`apps/server/src/api/dtos/participation.dto.ts:52-60`) — so the /speckit-analyze report's C1 finding is real: no single call returns this. The resolved fetch algorithm, using only existing endpoints:

1. `adminApi.listMinistries()` → ministries the current leader leads/sub-leads.
2. `adminApi.listPlanningCycles({ state: 'locked' })` → **this is the authoritative "cycle set"**, resolving the A1 ambiguity between spec's singular "relevant cycle" (FR-002) and plural "concurrently open cycles" (Assumption 1): it is the **union of every church-wide cycle currently in `locked` state** (not "most recent"), matching `ministry-tailoring-flow.md`'s "Cycle locked → visible to leader" transition — a cycle stops being tailorable once `archived`, and `draft` cycles have no events yet regardless.
3. Per ministry: `adminApi.listEvents({ ministryId })` → events; group by `planningCycleId` via the existing `buildCycleOptions` helper (`participation-tailoring.utils.ts`), then intersect with the locked-cycle-id set from step 2. `eventCount` per (ministry, locked cycle) falls out of this grouping for free — no extra call.
4. Per (ministry, locked cycle) pair that has ≥1 event: `adminApi.getCycleParticipation(cycleId, { ministryId })` → sum `events[i].slots.length` for the slot-inclusion count.

**Call volume**: `1 + 1 + ministries + Σ(ministries × their locked-cycle count)`. For the realistic case (a leader manages a handful of ministries, and per `ministry-tailoring-flow.md` typically one cycle is locked/actively tailored at a time), this is a small, bounded number of calls for a landing page — acceptable without a new aggregate endpoint. If a future church regularly runs many concurrent locked cycles, revisit with a dedicated backend aggregate.

**Rationale**: Keeps the feature's "no backend changes" plan decision intact while giving C1 and A1 concrete, implementable answers instead of leaving both as open hedges that would have blocked T006/T012/T013.

**Alternatives considered**: A new `GET /admin/ministries/tailoring-summary`-style aggregate endpoint — would reduce call count to 2, but is out of scope for a frontend-reorganization feature per the plan's explicit "no new API surface" decision; revisit only if the N+1 pattern proves to be a real measured problem.

## R11: Day strip replacing the month-grid calendar, and filters moving horizontal (Iteration 2)

**Decision**: Replace `tailoring-calendar.tsx`'s R3 month-grid (`react-day-picker` range variant) with a horizontally-scrollable strip of day cells — one column per day in `[cycle.startDate, cycle.endDate]`, each showing a day-of-week abbreviation over the day number. All three R3 signifiers (fixed cycle-bounds band, event-day dot marker, ring/outline active day-filter) carry forward unchanged in *meaning*; only their container goes from a 2D month grid to a 1D horizontal strip. Navigation: mouse click-and-drag, touch swipe, and a chevron button fixed at each end. `tailoring-filters.tsx` (name + time-of-day) moves from its current vertical sidebar column (`lg:grid-cols-[minmax(320px,0.6fr)_minmax(0,1.4fr)]` split in `$cycleId.tsx`) to a horizontal row directly beneath the new strip; the route's layout becomes a single top-to-bottom stack (day strip → filter row → slot list) instead of a sidebar+content split.

**Rationale**: The motivating case is a cycle spanning several months — at ~90+ day cells, a month-grid calendar (bounded to showing roughly one month at a time, requiring month-by-month pagination to reach a distant day) is a poor fit for "confirm slots, split shifts, and set headcounts" work that's meant to be quick between-service sessions (PRODUCT.md framing, same motivation as R7/R8). A horizontal strip scales to arbitrary cycle length without pagination, at the cost of needing a scroll/drag interaction that a grid didn't. Moving the filters horizontal follows directly once the sidebar column's main occupant (the calendar) is no longer sidebar-shaped — keeping filters in a now-empty-looking narrow column while the day strip spans full width above would be inconsistent, not merely suboptimal.

**Drag-scroll mechanism, scroll feel, and sticky behavior (resolved via `/impeccable shape`, 2026-07-12)**: Checked this codebase for prior art before shaping: `components/ui/scroll-area.tsx` is a vertical/utility wrapper (Radix `ScrollArea`), the only existing `overflow-x-auto` usage is on an unrelated dashboard widget, and neither the `@shadcn` nor `@intentui` registries in `components.json` have a first-party horizontal date-strip-with-drag component — confirmed there is no "reuse this existing shadcn block" answer here the way R3 had. Three sub-decisions, all confirmed by the user during the shape brief:

1. **Mechanism**: hand-rolled pointer events (`pointerdown`/`pointermove`/`pointerup`/`pointercancel` translating to `scrollLeft` delta on a native `overflow-x-auto` container), not a dependency. The actual need — horizontal drag-to-scroll, no slides/pagination/autoplay — is narrower than what a carousel library is built for, and this project has no existing carousel anywhere to justify the footprint. Chevron buttons still compose the existing `Button` + `ChevronLeftIcon`/`ChevronRightIcon` pattern already used in `tailoring-calendar.tsx`'s current month-nav chevrons — the Phase 5 "Strict shadcn/ui Adherence" rule requires reusing what exists *for the parts that do exist*, not inventing chevron buttons too.
2. **Scroll feel**: free momentum scroll, no snap-to-day-cell. Matches the original request's own phrasing ("click and slide"), avoids snap-point calculation against variable-width day markers, and doesn't need to coordinate with the already-spec'd keyboard arrow-key navigation (FR-020a) since that's a separate, precise selection method independent of scroll position.
3. **Sticky behavior**: the day strip + filter row become one sticky unit at the top of the workspace (replacing the current sidebar's `lg:sticky lg:top-4`), pinned while the slot list scrolls beneath. Dropping stickiness would regress the existing sidebar's behavior for exactly the long-list case this whole redesign targets — losing the day-filter control while scrolling a 90-day cycle's slot list defeats the point of filtering by day at all.

**Alternatives considered**: Keep the month grid and only add month-to-month quick-jump controls for long cycles — rejected, doesn't address the core complaint (a grid "lost in the screen" relative to how much of it is usable at a glance) and still requires pagination to reach a specific far-off day. A `<select>`-based day jumper as the *only* navigation (no visual strip) — rejected, loses the "see nearby days and event markers at a glance" property that both the grid and the strip provide and the grid alone doesn't lose. Snap-to-day scrolling — rejected per shape decision above. A scroll/carousel dependency — rejected per shape decision above. Non-sticky day strip — rejected per shape decision above.

**Keyboard navigation (resolved during `/speckit-clarify`, spec.md FR-020a)**: The strip also supports arrow-key roving focus (Left/Right moves focus one day, scrolling into view as needed; Enter/Space selects the focused day as the active filter) — matching the month-grid calendar's existing keyboard behavior so the swap loses no keyboard-only capability. This was flagged during clarification because a from-scratch custom widget has no keyboard behavior by default, unlike `react-day-picker`, and PRODUCT.md commits this app to no fine-motor-dependent-only interactions.

## R12: Slot row save model — Serving toggle and split each autosave/self-commit independently; headcounts save once per slot across all shifts (Iteration 2, corrected during `/speckit-clarify`)

**Correction note**: This entry originally described a single combined row-level save (split + headcount together). That was a misreading of the user's original request, caught and corrected during `/speckit-clarify` — see spec.md's `## Clarifications` Session 2026-07-12, first entry. The three-tier model below is the corrected, authoritative decision. `iteration-2-filters-and-row-save.md`'s Part C is superseded by this entry; that file has been annotated accordingly rather than silently left contradictory.

**Decision**: Split the current three independent mutations (`setParticipationInclusions` on checkbox change, `splitParticipationShifts` on its own "Save split" button, headcount upsert on its own per-shift "Save headcounts" button) into three independent tiers — not two, and never combined into one action:

1. **Serving toggle** (replaces the inclusion checkbox — see R12a below): still autosaves instantly via `setParticipationInclusions`, exactly as the current inclusion checkbox does. No change to this mutation's shape or trigger timing.
2. **Split configuration** (mode + shift count / manual spans): stays local, uncommitted state until the slot's own explicit "Save split" action is used. This button is dirty-gated — disabled whenever the split form matches its last-saved state, enabled only once it differs — so it does not fire on every increment of a shift-count number input, and it is completely independent of headcount state. Calls `splitParticipationShifts` unchanged.
3. **Headcounts** (every role, every shift, within that slot): also stays local, uncommitted state until the slot's own explicit "Save headcounts" action is used — but that one action now covers *every* role across *every* shift in the slot, replacing today's one-button-per-shift model. This is the actual "one save instead of many" improvement the user asked for — it was never about bundling split in. Calls the existing headcount-upsert mutation once per (shift, role) pair with a changed, valid value, in parallel.

**Per-slot dirty tracking**: two independent local (non-persisted, session-scoped) flags per slot — a split-dirty flag (split form differs from last-saved) and a headcount-dirty flag (any headcount draft differs from last-saved). Each clears independently, only on its own action's success. Both are new, smaller-grained siblings to the existing page-level `touchedParticipationIds` tracker (R8/T031) — neither replaces it. On either action's success for a slot, that slot's participation id is still added to `touchedParticipationIds` so the existing page-level "Save & request availability" batching (R4) is unaffected.

**Validation gate**: the headcount save is disabled whenever Serving is Yes and any shift's headcount is unset/zero — reusing the existing `parseValidHeadcounts` validity check already in `tailoring-slot-list.tsx` (T023b), extended to gate the new combined-across-shifts save rather than only the old per-shift save button. It must also surface *why* it's disabled, matching the standard already set this session for the page-level save button's copy. This gate applies only to the headcount save — the split save has no such gate and is never blocked by an unset headcount.

**Partial-failure semantics (resolved during `/speckit-clarify`, spec.md FR-022b)**: because the headcount save can now fire many upsert calls at once (every role × every shift in the slot), each call succeeds or fails independently — a failure on one MUST NOT roll back or re-flag ones that already succeeded server-side. Only the failed role/shift value(s) remain flagged unsaved/errored and are independently retryable, matching how the existing page-level "Save & request availability" batch action (R4) already behaves for its own per-participation calls. This was explicitly chosen over an all-or-nothing rollback because the headcount save's blast radius grew (one shift → potentially many), making all-or-nothing riskier than it was for the original per-shift button.

**Rationale**: Direct implementation of the corrected user decision. Keeping Serving instant matches the existing inclusion-checkbox precedent. Keeping split as its own dirty-gated (not autosave, not bundled) action matches the user's explicit reasoning: autosave-on-every-change would fire on every shift-count increment, and there's no meaningful validation gate on split the way there is on headcount, so a plain "has this changed" gate is sufficient. Combining *only* headcounts across shifts (not split) directly reduces the original three-saves-per-row friction the prior `/impeccable` critique flagged (`.impeccable/critique/2026-07-12T22-24-28Z__apps-web-src-routes-scheduling-tailoring.md` P1) to two independent, purpose-distinct actions per slot instead of one-per-shift-plus-one-per-split.

**Alternatives considered**: One global page-level save for everything (rejected — network-failure blast radius). A single combined split+headcount save (the original, incorrect reading of this decision — rejected once corrected: split and headcount have different persistence timing needs and no shared validation gate, so bundling them buys nothing and adds unnecessary coupling). Autosave-on-change for split (rejected — would fire on every increment of a number input, per explicit user reasoning). All-or-nothing headcount save (rejected — unnecessarily discards already-successful writes when the batch has grown larger than a single shift).

### R12a: Serving toggle replaces the raw checkbox

**Decision**: The current inclusion control (`<input type="checkbox">` in `tailoring-slot-list.tsx`, previously flagged as an accessibility gap for skipping the shadcn `Checkbox` component used everywhere else in this app) is replaced by an explicit "Serving" / "Not serving" two-state control, using the existing shadcn `Checkbox` component or an equivalent already-in-system two-state button pattern — not a new bespoke control.

**Rationale**: Directly fixes the previously-documented accessibility gap while implementing the user's explicit request for a named "yes we're serving / no we're not" affordance rather than an unlabeled checkbox. Two birds, one control — this was already on the polish backlog independent of this iteration.

## R13: Leave-guard extended to per-slot unsaved state (Iteration 2, wording corrected)

**Decision**: The existing navigation-blocking confirmation (R8, `useBlocker` in `$cycleId.tsx`, currently gated on `touchedParticipationIds.size > 0`) is extended so its blocking condition also includes "any slot has a pending split-dirty flag and/or a pending headcount-dirty flag" (R12's two independent per-slot dirty trackers), not only "at least one participation has already been successfully saved this session." The `AlertDialog`'s copy and Stay/Leave-anyway mechanics are unchanged — only the trigger condition (`shouldBlockFn`) is broadened, now checking two flags per slot instead of one.

**Rationale**: Explicit user decision (iteration-2-filters-and-row-save.md Decision 1, unaffected by R12's correction). Under the pre-Iteration-2 model, `touchedParticipationIds` was a reasonable proxy for "has unsaved work" because every edit auto-saved immediately (the only thing "unsaved" was the batched availability-fire, not the underlying data). Iteration 2 introduces a real gap: a slot can now have genuinely unpersisted split and/or headcount edits sitting in local state with nothing written to the server. Without this extension, a leader could navigate away mid-edit with zero warning and silently lose that slot's work — the exact failure mode this whole iteration's save-model redesign was motivated by avoiding ("don't want him to lose state"). Not extending the guard would make the dirty flags (R12) purely decorative for the one case where they matter most.

**Alternatives considered**: A second, separate confirmation dialog specifically for slot-level edits, distinct from the existing one — rejected as unnecessary UI proliferation; one guard with a broadened trigger condition is simpler and the leader-facing experience (an unsaved-changes prompt on exit) is identical either way. Leaving slot-level edits unguarded and relying solely on the visual unsaved indicators (FR-023) — rejected per explicit user decision; an indicator only helps if the leader notices it before navigating away, which is exactly the failure mode a blocking guard exists to prevent.

## R14: Split/headcount fields adopt `@tanstack/react-form` + `zod` (added during `/speckit-clarify`)

**Decision**: The split-form fields (`ManualSplitEditor`'s mode select, shift-count input, manual start/end spans) and the headcount fields (`tailoring-slot-list.tsx`'s per-role, per-shift number inputs) — the fields R12 is already rewriting for the new dirty-gated/combined save buttons — adopt `@tanstack/react-form` with `zod` schema validation, rather than continuing (or expanding) the current hand-rolled parsing/validation (`validateManualSpans`, `parseValidHeadcounts`). Both `@tanstack/react-form` and `zod` are already project dependencies and already used together in `apps/web/src/components/sign-in-form.tsx` and `sign-up-form.tsx` — this is adopting an existing, proven pattern, not introducing a new one.

The existing validation *logic* — manual-span bounds/ordering/overlap rules and headcount integer/positivity rules — is preserved and moved into the new `zod` schema as its source of truth, not rewritten from first principles, consistent with this feature's established "logic unchanged, structure rewritten" precedent (R2).

**Scope**: Limited to the fields this iteration is already touching for the save-model rework. Not a repo-wide retrofit of every form in the app, and not applied to fields this iteration doesn't otherwise modify.

**Rationale**: User-flagged during clarification: "most of those inputs have no validation whatsoever" (accurate — `parseValidHeadcounts` is a manual `parseInt` + bounds check with no schema, no field-level error surfacing beyond a disabled button) and this codebase already has an established, working form-library pattern one directory over. Reusing it here is more consistent with the codebase than inventing a third validation approach (manual parsing was already two: `validateManualSpans` for spans, `parseValidHeadcounts` for headcounts) on top of the two that already exist.

**Alternatives considered**: Continue extending the manual `parseInt`/manual-bounds-check approach to cover the new dirty-gating logic — rejected, adds a third bespoke validation approach to a codebase that already has an established library-based one sitting unused nearby. `react-hook-form` or another form library — rejected, not a project dependency; `@tanstack/react-form` already is, and this codebase's constitution favors reuse of what exists.

## R15: Cycle-list "Status" — domain-model contradiction found and resolved (Iteration 3)

**Decision**: User Story 2's cycle-picker Status badge, as first shipped this session, displayed `PlanningCycle.state` — always `locked`, since this screen is already hard-filtered to locked cycles server-side. This was flagged by the user as showing the wrong thing, and further investigation while drafting Iteration 3 surfaced a real contradiction in the corrected request, resolved via `AskUserQuestion` before any implementation:

The actual `MinistryParticipation` lifecycle (`apps/server/src/domain/entities/ministry-participation.ts`) is a strict 4-stage sequence enforced by guarded transitions: `tailoring → availability_fired → rostering → published`. `published` is only reachable via `MinistryParticipation.publish()`, which throws unless `state === 'rostering'` and completion is 100% (or explicitly confirmed below-full) — a phase downstream of, and outside, this feature's own scope (rostering/assignment is a separate flow). The user's initial correction proposed a 3-way status (`Not started` / `In progress` / `Published`) where the "Published" boundary was ambiguous against this real lifecycle: it could plausibly mean either the real terminal `published` state, or the much earlier `availability_fired` milestone (the point at which *this* feature's leader-facing work is actually done). These two readings differ by two full lifecycle stages and produce very different UI behavior — under the `availability_fired` reading, most cycles reach "Published" the moment the leader finishes tailoring; under the real `published` reading, cycles sit in "In progress" long after the leader is done, until a separate rostering flow elsewhere finishes them.

Resolved via `AskUserQuestion`: the leader-facing terminal status means the real `published` state. This is deliberate, not a default — the user confirmed it explicitly after the tradeoff was surfaced. Consequence: "In progress" is a wide bucket, spanning touched-but-still-`tailoring`, `availability_fired`, and `rostering`. A separate, finer signal (has availability been fired for every participation in the cycle) is still needed independently for the Builder Events unlock rule (FR-035, R16) — that boundary sits inside the "In progress" bucket and cannot be recovered from the 3-way status alone.

**Rationale**: Implementing the ambiguous reading either way, unresolved, risked shipping a status that reads as "wrong" to the leader in one of two equally-plausible ways — either cycles appear "done" the moment tailoring work stops (misleading, since rostering/publishing hasn't happened) or cycles sit in a vague "in progress" state for potentially weeks after the leader's own work is genuinely finished (unhelpfully coarse). Surfacing the contradiction and asking, rather than picking silently, matches this feature's established pattern (R3, R7, R11 were all resolved the same way) of treating genuinely ambiguous UX/domain-mapping decisions as clarification points, not silent defaults.

**Alternatives considered**: Map the terminal status to `availability_fired` instead — rejected by explicit user decision; would have made "Published" a much larger and less meaningful bucket, and would have collided with FR-035's Builder Events unlock rule needing exactly this boundary for a different purpose. Add a new, independent "leader marks tailoring complete" flag decoupled from the real state machine entirely — considered and rejected in favor of the simpler reading (real `published` state), since it would require its own new mutation/endpoint beyond the read-side aggregation this iteration already needs, for a signal the real lifecycle can already express once "In progress" is understood to span multiple real states.

## R16: Cycle-level status aggregation rule and the `touchedAt` field (Iteration 3)

**Decision**: A cycle can span multiple events, each with its own `MinistryParticipation` record potentially in a different state. Rolling this up to one cycle-level status (R15) uses an **"all participations must reach X"** rule for both boundaries: "Not started" only when *every* participation's `touchedAt` is null; "Published" only when *every* participation's `state` is `published`. Any other combination — including a cycle where some events are published and others are still mid-tailoring — reads as "In progress."

Separately, no field exists today to distinguish "never touched" from "touched but still in `tailoring` state" — `MinistryParticipation.state` alone can't express this, since both cases share the same `state` value. Resolved via `AskUserQuestion` in favor of a new nullable `touched_at` timestamp column on `ministry_participation` (`packages/db/src/schema/participation.ts`), set once on the first inclusion/split/headcount write for that participation and never overwritten afterward.

**Rationale (aggregation rule)**: "All must reach X" was not put to the user as an explicit clarification question — it's the reading that matches how the three status words would naturally be understood by a leader ("not started" implies nothing anywhere has begun; "published" implies everything is done), and an "any" rule for either boundary would produce a status that undersells or oversells the cycle's real completeness (e.g. "any published" would call a cycle "Published" while 9 of its 10 events are still mid-tailoring). Flagged in spec.md's Assumptions as a documented default open to correction against real seeded data during implementation, not a re-litigated open question.

**Rationale (`touchedAt` over row-existence inference)**: The alternative — inferring "touched" from the existence of `ParticipationSlotInclusion`/`Shift`/`SlotRequirement` rows tied to a participation — was considered and rejected because it's ambiguous in a real, expected case: a leader who reviews a slot and explicitly decides their ministry serves none of it produces zero inclusion rows, which is indistinguishable from a participation nobody has looked at yet. A dedicated timestamp removes this ambiguity at the cost of one small migration and one write-path change (set once, guarded, in the same manager methods that already handle `setInclusions`/`splitShifts`/`upsertRequirement`).

**Alternatives considered**: Infer "touched" from row existence (rejected above). Track "touched" client-side only, session-scoped, matching how `touchedParticipationIds` already works in `$cycleId.tsx` (R8) — rejected, since that tracker is explicitly session-scoped/non-persisted by design (R8, R13's own rationale), while this status must survive across sessions and be visible to the leader on their *next* visit, which is the entire point of a cycle-list-level "where did I leave off" status. A cycle-level (not participation-level) `touchedAt`/status field, set directly on some cycle-ministry join record — rejected in favor of per-participation, since the existing data model has no such join record today and per-participation is both a smaller change (extends an existing entity) and the correct granularity for the "all participations" aggregation rule above to operate over.

**Correction (2026-07-13, post-`/speckit-analyze`, findings I1/I2)**: The first draft of this decision implicitly assumed the aggregation query would only ever run over cycles the ministry already has ≥1 event in — i.e., zero participations was never a case the aggregation had to handle, because such cycles would simply never be queried. `/speckit-analyze` caught that this silently made FR-033's "Not part of" Ministry Involvement filter value impossible: there was no data path for cycles the ministry isn't part of at all. The aggregation is corrected to run over **every locked cycle church-wide**, not just ministry-inclusive ones, with an explicit `isPartOf` boolean per cycle (`isPartOf = eventCount > 0`). This forces two more rules the "all participations" language above didn't need to state explicitly while the zero-participation case was assumed impossible:

- **`status` for `isPartOf = false`**: `'not_started'`. This is a defensible reading of "all participations must reach X" over an empty set (vacuously true for every bucket), but resolved explicitly to `'not_started'` rather than left as an implicit vacuous-truth artifact, since "not started" is the only one of the three labels that reads correctly to a leader glancing at a cycle their ministry has never touched.
- **`availabilityFiredForAll` for `isPartOf = false` (or `eventCount = 0`)**: explicitly **`false`**, NOT the vacuously-true result of "every participation (of zero) has fired availability." This is the one place vacuous truth is actively wrong, not just unhelpful: FR-035 gates the Builder Events button on this boolean, and a vacuously-true value would enable that button for a cycle the ministry has no involvement in at all — the manager method computing this MUST special-case `eventCount === 0` before applying the "every participation" reduction, not apply the reduction blindly to an empty array.

See data-model.md's "New in Iteration 3" section for the corrected response shape and query scope, and spec.md FR-032/FR-033 for the requirement-level correction.
